# 醒来先看：KaTrade 当前可用状态与继续开发说明

更新时间：2026-05-10

这份文档放在根目录 `doc/`，目的是让使用者和后续接手的 Codex 先读这里，快速知道平台当前能做什么、怎么启动、哪里看日志、下一步继续做什么。

## 1. 最短使用路径

双击根目录：

```text
/Users/snlnfy/Documents/量化交易/启动交易平台.command
```

当前启动脚本会做这些事：

1. 先调用 `quant-system/stop.sh` 清理旧的本地 platform、historyd、realtime_engine 进程，避免端口冲突。
2. 按需编译 C++20 `realtime_engine` 和 `backendd`。
3. 启动 `historyd`，默认端口 `8790`。
4. 启动 C++20 `backendd`，默认端口 `8791`。
5. 启动平台 Web 服务，默认端口 `8787`。
6. 平台启动后自动连接 OKX 公共行情流。
7. 默认尝试恢复虚拟盘 runner。
8. 虚拟盘 runner 会走 OKX simulated trading 自动提交门禁，只允许模拟盘、post_only 限价单，不允许真实实盘、市价单、IOC 或 FOK。

打开页面：

```text
http://127.0.0.1:8787/dashboard
http://127.0.0.1:8787/paper
http://127.0.0.1:8787/orders
http://127.0.0.1:8787/agents
http://127.0.0.1:8787/risk
```

双击根目录：

```text
/Users/snlnfy/Documents/量化交易/关闭交易平台.command
```

会停止本地服务和本地 C++ runner。注意：关闭平台不会自动撤销 OKX 模拟盘已有挂单，因为撤单是交易动作，必须在平台订单链路里执行和审计。

## 4. 现在“盈亏贡献”是谁带来的

当前 `/agents` 页面的盈亏贡献已经改成从真实成交生命周期读：

```text
order_journal.order.fill.close_net_pnl
```

也就是说，它统计的是平仓成交带来的净盈亏，而不是旧的 Agent 资金快照。

归因顺序：

1. 优先读订单上的 `strategy_attribution`，按策略贡献权重拆分。
2. 没有拆分权重时，读 `strategy_id / agent_id / trading_unit_id`。
3. 老历史订单如果没有记录这些字段，会显示为 `unknown`，不会伪造贡献来源。

新增接口：

```text
GET /api/agent/attribution?limit=20000&recent=50
GET /api/backend/account/portfolio?limit=20000&recent=50
GET /api/backend/account/positions?limit=20000
GET /api/backend/account/pnl?limit=20000&recent=50
GET /api/backend/account/attribution?limit=20000&recent=50
GET /api/backend/orders/local_repair_plan?min_age_seconds=300&max_orders=20
GET /api/backend/orders/broker_terminal_sync_plan?max_orders=20
GET /api/backend/orders/stale_broker_reconcile_plan?min_age_seconds=180&max_orders=20
GET /api/paper/broker_terminal_sync_plan?maxOrders=20
POST /api/paper/broker_terminal_sync
GET /api/paper/stale_broker_reconcile_plan?minAgeSeconds=180&maxOrders=20
POST /api/paper/stale_broker_reconcile
```

其中 `/api/backend/account/*` 是 C++20 `backendd` 的账户读模型，已经能从 `order_journal` 重放：

- 当前净持仓、均价、最近成交价、名义敞口。
- 平仓净盈亏、平仓手续费、总成交手续费。
- 策略、Agent、交易单元归因。
- 最近平仓/成交明细。
- 资金曲线端点 `/api/backend/account/equity`：默认返回最新报告曲线，并附带 C++ 从最近 paper session 的 `order.fill` 重放出来的 realized-only 曲线和保守 ticker 盯市曲线；如需排查全历史可传 `session=all`。
- UI 已经在 `/dashboard` 的“净值曲线”和 `/risk` 的“资金曲线”接入该端点。页面会同时显示“报告净值(含浮盈亏)”、“C++盯市净值”和“C++成交回放(仅已实现)”，并在摘要里展示 session、报告最终权益、C++盯市权益、C++已实现权益、平仓净盈亏、未实现盈亏和累计手续费。
- 账户计算主逻辑已经从 `quant-system/src/backend/api/route_registry.cpp` 拆到 `quant-system/src/backend/account/account_read_model.cpp`。以后补反向合约估值、资金费率、保证金、Agent 资金快照时，应优先扩展 `account_read_model`，路由层只保留 query 解析和 JSON 输出。
- 账户 API 序列化和注册已经继续拆到 `quant-system/src/backend/account/account_routes.cpp`，订单日志归约已经拆到 `quant-system/src/backend/order/order_read_model.cpp`，通用 query/JSON 工具已经拆到 `quant-system/src/backend/common/route_utils.cpp`。后续多人协作边界见 `doc/12-模块拆分与多人协作边界.md`。
- C++ 源码已经开始按模块目录放置：`backend/api`、`backend/common`、`backend/account`、`backend/order`、`execution`、`portfolio`、`risk`、`data`、`engine` 等目录分别承接自己的实现文件。新增 C++ 实现不要再直接放到 `quant-system/src` 根目录。

C++ 盯市口径目前是保守实现：

1. 优先使用同名 OKX 合约 ticker。
2. 找不到合约 ticker 时，使用基础币种现货 ticker fallback，并在持仓字段 `mark_source=spot_ticker_fallback` 标出。
3. 线性合约用 OKX 缓存元数据 `ct_val` 做张数到币数量的换算。
4. 反向合约暂不计算未实现盈亏，会显示 `inverse_contract_unmarked`，避免错误估值。

注意：历史日志里如果只有 `tick-maker-rebalance / paper-tick-rebalance` 这类调仓标签，而没有真实基础策略 ID，C++ 会把它归入 `unknown`。这比把调仓标签伪装成策略贡献更诚实，后续要继续改的是新订单必须带完整 `strategy_attribution`。

当前旧历史数据大概率还有很多 `unknown`，这是因为早期订单日志没有保存真实策略归因。新订单会开始带上策略、Agent、交易单元字段。

订单自动化维护也开始迁到 C++：

- `/api/backend/orders/consistency` 负责诊断本地订单、执行轨迹和 OKX 审计是否一致。
- `/api/backend/orders/local_repair_plan` 负责给出本地-only 陈旧虚拟盘订单的 dry-run 修复计划。
- `/api/backend/orders/broker_terminal_sync_plan` 负责找出“OKX 审计已终态、本地仍活跃”的回补候选。
- `/api/backend/orders/stale_broker_reconcile_plan` 负责找出“本地活跃且有 OKX 单号但已陈旧”的主动查单/撤单候选。
- C++ 订单维护规则已经拆到 `quant-system/src/backend/order/order_maintenance.cpp`，路由层只负责读日志和输出 JSON。后续接入 C++ 查单、撤单、OMS apply 时，应优先扩展这个模块，而不是继续堆 `route_registry.cpp`。
- `quant-system/apps/order_maintenance_check/main.cpp` 是订单维护规则的 C++ 回归测试，覆盖本地假活跃单、已 submitted 保护、broker 终态同步、陈旧 broker 对账和 `max_orders` 上限。后续改订单自动化时必须跑 `make order_maintenance_check` 或 `make validate`。
- `quant-system/apps/account_read_model_check/main.cpp` 是账户读模型回归测试，覆盖开仓、部分平仓、策略贡献、线性合约 `ct_val` 折算和 ticker 盯市权益。后续改 PnL、资金曲线、合约估值时必须跑 `make account_read_model_check` 或 `make validate`。
- Python `/api/paper/local_order_repair_plan` 已优先读取 C++ 计划；只有 backendd 不可用时才回退 Python 旧逻辑。
- Python `/api/paper/broker_terminal_sync_plan` 已优先读取 C++ broker 终态回补计划。
- Python `/api/paper/broker_terminal_sync` 是受控 apply 入口，必须带 `confirm=SYNC_OKX_TERMINAL_PAPER_ORDERS`，只写本地 `order.broker_sync`，不会向 OKX 发送下单或撤单。
- Python `/api/paper/stale_broker_reconcile` 是受控主动对账入口：普通确认 `confirm=RECONCILE_STALE_OKX_BROKER_ORDERS` 只查 OKX 并同步终态；如果要撤仍 live 的模拟盘挂单，还必须额外带 `cancel_confirm=CANCEL_STALE_OKX_SIMULATED_ORDERS`。
- C++ 计划不会直接写 journal，也不会撤 OKX 单。真正写 `order.expired` / `order.broker_sync` 的动作仍由 Python 受控入口完成。
- 任何带 OKX `ordId/clOrdId`、最新执行轨迹为 `submitted`、或 OKX 审计显示仍可能存在的订单，都会被保留给 OKX 对账/撤单/成交回补链路，不会本地伪过期。

## 5. 当前实现到什么程度

已经具备：

- OKX/欧意作为当前唯一券商方向。
- OKX simulated trading 配置、状态检查、提交门禁。
- 默认合约链路，优先 SWAP/FUTURES，post_only 限价挂单。
- 1 USDT 基础委托到 OKX 合约 `minSz/ctVal` 的折算和最小数量抬升。
- 活跃挂单上限，当前默认 10。
- 陈旧 OKX 模拟盘挂单自动维护、订单同步、成交回补、OKX 终态回补、本地订单修复。
- C++20 策略、风控、OMS、模拟 broker、组合账本、回放检查和实时行情质量 runner 雏形；C++ 回测成交流已经改为 `OMS -> SimulatedBrokerGateway -> ExecutionReport -> PortfolioBook`，不再由 `TraderEngine` 合成成交。
- `traderd` 报告已经带基础可追溯元数据，包括数据源、数据 hash、配置 hash、代码版本占位、成交模型版本、覆盖区间、bar 数和品种数。
- Python 本地 UI/API 作为过渡壳层。
- `/paper` 虚拟盘页面实时刷新。
- `/orders` 订单中心，包含 C++ 一致性巡检、本地订单生命周期、OKX 审计、执行轨迹、失败聚类、执行质量。
- `/agents` 交易 Agent 页面，展示资金、策略贡献和归因摘要。
- `/risk` 运维/风控状态。
- `/market` 行情页，支持 OKX 公共行情和 tick/stream 状态查看。
- UI 二次重构已经开始：总览页增加运行态摘要条和 C++ 资金曲线摘要，顶部增加 OKX/虚拟盘/C++ 状态胶囊，虚拟盘页增加运行快照，订单页已经接入 C++ 一致性巡检、订单生命周期和 OKX 提交记录，风控页已经能直接查看资金曲线。
- 运维预检已经修正：`realtime` 模式也必须有可追溯 OKX 逐笔/stream 来源；缺少逐笔来源时不再显示“通过”，会在 readiness 中标成阻断/警告。
- C++20 `backendd` 主后端骨架已开始落地：支持命令模式和长驻 HTTP 模式，已接管订单、执行 trace、行情质量、账户持仓、PnL 归因的第一版只读 read model；`/api/backend/orders/consistency` 已能输出具体问题订单、异常类型、最新执行轨迹、最新 OKX 审计状态和建议动作，`/api/backend/orders/local_repair_plan` 与 `/api/backend/orders/broker_terminal_sync_plan` 已能输出订单修复/回补计划。详细边界和迁移计划见 `doc/10-C++20-backendd-主后端设计与迁移计划.md`。

仍未完全生产化：

- OKX 私有下单、撤单、对账和大量风控门禁仍有很多逻辑在 Python `apps/platform/server.py`，目标是逐步迁移到 C++20。
- `realtime_engine` 当前主要负责只读行情质量和 tick 处理，`backendd` 已开始承担订单、账户持仓、PnL 和归因 read model，但尚未接管策略决策、OMS 和 OKX gateway。
- UI 仍是原生 HTML/CSS/JS，已改善但还不是成熟交易终端。
- Agent 调仓、交易单元杠杆分配还处于“可写状态和门禁裁剪”阶段，尚未形成完整闭环。
- 历史旧订单归因不完整；C++ 不会伪造来源，会把没有真实策略字段的成交归到 `unknown`。
- 生产环境还需要更强的配置隔离、密钥权限隔离、长期进程守护、告警和回滚流程。

## 6. 下一步优先任务

按优先级继续推进：

1. 把 C++ 一致性巡检进一步接入 OKX 对账/撤单/成交回补：目前本地-only 修复、broker 终态回补、有 OKX 单号的陈旧挂单主动查单/撤单计划都已由 C++ 生成；Python 已有受控入口执行查单、终态同步和模拟盘撤单。下一步要把这套 apply 逻辑继续下沉到 C++ OMS/gateway。
2. 在 C++ 账户读模型上继续补交易账户口径：当前已经有持仓、平仓 PnL、归因、资金曲线和线性合约保守盯市，下一步要补反向合约估值、资金费率、保证金占用和 Agent capital snapshots。
3. 把 OKX 执行、订单状态机、合约元数据缓存、数量折算、失败码归因继续迁到 C++20。
4. 把 `apps/platform/server.py` 拆模块，Python 只保留 UI/API 壳层。
5. 继续完善虚拟盘 runner 的可视状态：把上次 OKX 提交结果、逐笔来源缺口、C++ runner 状态和门禁阻断项合成一个更清晰的执行面板。
6. 补策略级别的风险预算、交易单元聚合、Agent 杠杆建议闭环。
7. 继续 UI 二次重构：订单详情抽屉、策略配置和策略实例分离、行情 tick 明细视图、移动端表格密度。
