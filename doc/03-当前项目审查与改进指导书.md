## 2. 和 Waylandz 指导书的差距

### 2.1 数据工程差距

Waylandz 第06课强调数据工程不是“拿到数据就用”，而是要解决供应商差异、交易所时间、缺失、复权/合约规格、坏点、版本、可回放等问题。

当前项目已有：

- `historyd` 和 OKX 历史接口。
- OKX 公共 WS journal：`logs/market_stream/okx_public.jsonl`。
- 非生产数据来源检查：`NON_PRODUCTION_DATA_TOKENS`。
- 黄金数据没有配置时不再造假，这是正确方向。
- C++ `FeatureEngine` 已经开始按品种分组计算特征。

差距：

- 数据版本没有成为回测和报告的一等字段。报告里还没有稳定的 `dataset_id/source/content_hash/coverage`。
- OKX 合约元数据仍有硬编码和实时缓存混用，`ctVal/minSz/lotSz/tickSz` 没有完全收敛到 C++ `InstrumentMaster`。
- `apps/realtime_engine/main.cpp` 使用字符串搜索解析 JSON，不是结构化解析；行情 journal 格式稍有变化就可能静默错。
- C++ 实时质量报告源码和实际平台 gate 断裂。
- `config/default.cfg` 仍默认 `replay_path=data/sample_bars.csv`，对生产/模拟自动交易来说容易误用。

### 2.2 回测系统差距

Waylandz 第07课强调回测的危险点：未来函数、过拟合、幸存者偏差、交易成本、滑点、成交概率、样本内外拆分和 walk-forward。

当前项目已有：

- `BacktestEngine`、`ReplayDataSource`、`replay_check`。
- 多策略、Regime、组合、风控、账本。
- 参数扫描和 walk-forward 的平台接口雏形。
- 成本、滑点、部分成交参数。

差距：

- 已修复：`make check` 当前恢复可用，并加入了执行模型检查。
- 已修复：C++ `TraderEngine` 不再自己合成成交，订单通过 OMS 提交、由 `SimulatedBrokerGateway` 根据成交量参与率和行情快照生成回报。
- 已修复：`SimulatedBrokerGateway` 的成交量参与率模型已经进入 `TraderEngine::run_cycle()` 主流程。
- 回测报告缺少数据版本、代码版本、配置 hash、成交模型版本、样本内/样本外标记。
- 策略“洗策略”和参数扫描需要更强的防过拟合报告，而不是只看收益曲线。

### 2.3 执行系统差距

Waylandz 第19课的核心是：策略信号不等于成交。中间必须经过 OMS、EMS、成本估计、委托状态机、券商回报、撤单、失败重试、对账。

当前项目已有：

- OKX simulated trading 提交、撤单、订单详情、审计、execution trace、execution ledger。
- 活跃挂单上限、陈旧挂单自动撤单、tradeability 检查。
- C++ `validate_okx_spot_order`、`validate_okx_derivatives_order`、`evaluate_okx_tradeability`。
- Python 自动提交只允许 simulated trading，这是正确安全边界。

差距：

- 私有 OKX 提交仍在 Python 大文件里，C++ 还没有 broker adapter。
- 已修复：C++ 回测/实时主循环已经由 OMS 接收 broker fills，`TraderEngine` 不再合成 fill。
- 仍需改进：撤单、成交、部分成交、拒单、超时等状态在 C++ 和 Python 仍有两套账本，后续要继续收敛。
- `broker_status()` 还显示“SPOT/cash limit/post_only”，但配置和 README 又说合约默认 SWAP/FUTURES，用户会被误导。
- 当前 C++ 质量门禁被 Python stub 绕过，自动提交前的实时数据可信度下降。

### 2.4 风控和资金管理差距

Waylandz 第15课强调 Risk Agent 必须独立，有一票否决权；第16课强调组合构建不是信号平均。

当前项目已有：

- C++ `RiskAgent`、压力测试、风险预算、kill switch、drawdown、vol scale。
- 交易单元杠杆建议和 agent leverage proposal。
- `RiskBudgetAllocator` 和 execution trace 的风险快照。

差距：

- 风控仍分散在 Python 与 C++，没有唯一的 pre-trade risk service。
- `cxx_market_quality_guard()` 永远 ready，削弱运行期硬门禁。
- 杠杆 agent 目前应只做建议，但需要更明确的“统计事实 -> agent 建议 -> risk 裁剪 -> 交易单元执行”闭环日志。
- 合约杠杆、交易所杠杆、有效杠杆、交易单元杠杆之间的定义需要写成统一公式，并在 C++ 单测覆盖。

### 2.5 生产运维差距

Waylandz 第20课强调生产不是“程序能跑”，而是可观测、可恢复、可停机、可追责、可报警。

当前项目已有：

- `/api/ops/readiness`、alerts、incidents、freeze。
- startup logs、paper state、event journal、order journal。
- 一键启动和 stop.sh 雏形。

差距：

- 当前根启动脚本与 README 不一致；没有根级关闭脚本。
- 启动脚本不会启动 paper runner，不会检查 `make check`，也不会检查 OKX simulated readiness。
- `启动交易平台.command` 直接 `kill -9` 端口进程，可能杀掉用户手动跑的其他服务。
- `server.py` 18,820 行、536 个函数、120 个 `/api/` 路由判断，后续维护成本过高。
- 没有统一 supervisor，进程异常退出后无法自动恢复。

### 2.6 典型死亡方式对照

Waylandz 附录 B 讲的是量化系统常见死亡方式。当前项目最接近这些风险：

- 数据源不可信：C++ 质量 gate 被 stub，sample 源仍是默认配置。
- 回测漂亮但不可执行：回测成交由引擎直接合成，没有真实 OMS/fill 生命周期。
- 实盘和回测两套逻辑：Python OKX 自动提交和 C++ 回测执行不是同一条执行链。
- 监控看起来很多，但关键门禁被绕过：UI 能展示很多状态，但 `cxx_market_quality_guard()` 永远 ready。
- 文档漂移：README 描述不存在的入口和目录，开发者按文档会走错。
