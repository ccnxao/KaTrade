# 模块拆分与多人协作边界

更新时间：2026-05-10

这份文档解决一个实际问题：平台已经大到不能靠一个人长期维护。后续开发要按模块分工，每个人只负责清晰的一块，避免所有交易逻辑继续堆进 Python 大文件或 C++ 路由大文件。

当前原则：

1. 除 UI 和过渡壳层外，交易核心逐步迁到 C++20。
2. OKX 是当前唯一券商方向，其他券商不要再扩展。
3. C++ 模块按“领域模型 -> 路由/API -> UI 壳层”分层。
4. 任何模块都不能绕过 journal、执行轨迹、审计和回归测试。
5. 新功能必须先明确 owner 模块，再写代码。

## 1. 当前推荐分工

| 分工角色 | 主要目录 | 主要职责 | 不能随便改 |
| --- | --- | --- | --- |
| C++ Backend Core | `quant-system/src/backend`、`include/qt/backend` | 后端 read model、路由、状态恢复、后续 OMS/OKX gateway | 不直接写 UI，不把交易规则塞进 JSON 序列化函数 |
| Strategy Engine | `quant-system/src/strategies`、`include/qt/strategies*`、后续 `src/strategy_runtime` | 策略定义、策略实例、tick/bar 驱动、信号输出 | 不直接下单，不直接访问 OKX 私有接口 |
| OMS / Execution | `quant-system/src/execution/oms.cpp`、`include/qt/oms.hpp`、后续 `src/execution/*` | 委托状态机、订单生命周期、成交回报、撤单重试 | 不计算策略信号，不绕过 risk |
| Risk / Capital | `quant-system/src/risk`、`include/qt/risk`、`src/portfolio/portfolio_book.cpp` | 交易前风控、杠杆、保证金、资金占用、压力测试 | 不直接调用 OKX 下单 |
| Data / Market | `quant-system/src/data`、`apps/realtime_engine`、`logs/market_stream` | OKX 公共行情、tick 质量、合约元数据、数据版本 | 不产生策略订单 |
| Python Shell | `quant-system/apps/platform/server.py` | UI 静态服务、配置保存、Kimi/Agent 适配、C++ 代理 | 长期不应保留核心交易状态机 |
| Frontend UI | `quant-system/apps/platform/static` | 页面、表格、图表、实时刷新、运维可视化 | 不在前端做交易风控判定 |
| Ops / Launch | 根目录 `.command`、`quant-system/start.sh`、`stop.sh` | 一键启动、关闭、日志、预检、进程守护 | 关闭平台不等于自动撤 OKX 订单 |

## 2. C++ backendd 目前已经拆开的模块

### 2.1 `route_registry`

文件：

```text
quant-system/include/qt/backend/api/route_registry.hpp
quant-system/src/backend/api/route_registry.cpp
```

职责：

- 保存 `path -> handler` 映射。
- 解析 HTTP route 和 query string。
- 注册总路由。
- 承担少量平台汇总路由，例如 `/api/backend/summary`。

现在不应该再塞进去：

- 账户 PnL 计算。
- 订单日志归约。
- 复杂 query/JSON 工具。
- OKX 下单、撤单、查单。
- 策略决策。

本轮已把账户 API 和订单归约从这里拆出去。`route_registry.cpp` 已经从 1000 多行继续下降到约 700 行，但还需要下一轮继续拆 `order_routes`。

### 2.2 `route_utils`

文件：

```text
quant-system/include/qt/backend/common/route_utils.hpp
quant-system/src/backend/common/route_utils.cpp
```

职责：

- 解析 query 参数：`query_int`、`query_int_any`、`query_bool_any`。
- 输出通用 JSON：文件快照、JSON lines 数组、`map/set` JSON。

适合谁维护：

- C++ backend/API 工程师。

修改注意：

- 这里是所有路由共享工具，不能放业务规则。
- 如果增加新的 query 类型，要写成通用函数，不要读具体业务文件。
- 修改后至少跑：

```bash
cd /Users/snlnfy/Documents/量化交易/quant-system
make backendd
./backendd --root . --config config/default.cfg --route /api/backend/summary >/dev/null
```

### 2.3 `order_read_model`

文件：

```text
quant-system/include/qt/backend/order/order_read_model.hpp
quant-system/src/backend/order/order_read_model.cpp
```

职责：

- 从 `logs/order_journal/orders.jsonl` 归约当前订单状态。
- 从 `logs/execution_trace/decisions.jsonl` 归约最新执行轨迹。
- 从 `logs/okx_audit/orders.jsonl` 归约 OKX 审计状态。
- 统一订单状态命名，例如 `submitted/live -> pending`，`canceled -> cancelled`。

适合谁维护：

- OMS / Execution 工程师。
- 后续做 OKX 对账、撤单、成交回补的人也会用它。

不能做：

- 不负责决定是否撤单。
- 不负责向 OKX 发请求。
- 不负责写 journal。

修改注意：

- 它是订单中心和一致性检查的输入层。状态归约一旦错，UI 会误判订单是否还活着。
- 新增订单事件类型时，先在这里把字段归约清楚，再交给 `order_maintenance` 做判断。
- 修改后至少跑：

```bash
cd /Users/snlnfy/Documents/量化交易/quant-system
make backendd order_maintenance_check
./backendd --root . --config config/default.cfg --route '/api/backend/orders/center?limit=20&consistency_limit=2000' >/dev/null
```

### 2.4 `order_maintenance`

文件：

```text
quant-system/include/qt/backend/order/order_maintenance.hpp
quant-system/src/backend/order/order_maintenance.cpp
quant-system/apps/order_maintenance_check/main.cpp
```

职责：

- 基于订单状态、执行轨迹、OKX 审计生成一致性问题。
- 判断本地-only 假活跃单是否能本地过期。
- 判断 OKX 已终态但本地未终态的订单是否需要回补。
- 判断陈旧 OKX 挂单是否需要主动查单/撤单。

不能做：

- 当前仍只产出 dry-run 计划，不直接写 journal，也不直接撤 OKX 单。
- 后续如果要迁 C++ apply，也应该新建明确的 OMS/gateway apply 模块，而不是把副作用塞回这里。

修改注意：

- 必须同步补 `order_maintenance_check`。
- 对带 `ordId/clOrdId` 或最新 trace 为 `submitted` 的订单要保守，不能本地伪终态。

### 2.5 `account_read_model`

文件：

## 4. 多人开发规则

### 4.1 新功能先选 owner 模块

例子：

- “为什么订单没撤”：先看 `order_read_model` 和 `order_maintenance`。
- “为什么 PnL 不对”：先看 `account_read_model`。
- “为什么接口字段没有”：看对应 `*_routes`。
- “为什么前端没刷新”：看 `apps/platform/static/app.js`。
- “为什么 OKX 返回 All operations failed”：后续看 `okx_gateway` 和审计日志。

不要直接去改 `server.py` 或 `route_registry.cpp`。

### 4.2 每个模块必须有验证入口

当前已有：

```text
apps/order_maintenance_check/main.cpp
apps/account_read_model_check/main.cpp
```

后续每拆一个核心模块，都应增加对应 check：

```text
apps/order_read_model_check/main.cpp
apps/okx_quantity_check/main.cpp
apps/risk_budget_check/main.cpp
apps/strategy_runtime_check/main.cpp
```

### 4.3 C++ 和 Python 的边界

Python 可以做：

- UI 静态文件服务。
- 配置表单。
- Kimi/Agent API 适配。
- C++ API 代理。

Python 不应继续长期做：

- 策略实时决策。
- 订单状态机。
- OKX 私有交易。
- PnL 主账本。
- 风控一票否决。

### 4.4 UI 不做核心判定

前端只能展示：

- 当前策略状态。
- 当前订单状态。
- 当前风险状态。
- 当前账户状态。
- API 返回的诊断和建议动作。

前端不能自己决定：

- 订单是否能发。
- 是否撤单。
- 是否加杠杆。
- PnL 是否有效。
